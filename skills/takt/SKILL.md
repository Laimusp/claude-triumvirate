# Система ТАКТ

Дисциплина поэтапной разработки. **Один такт = один этап задачи**. Между тактами — обязательное ТБ-ревью коммита.

## Принципы
- Никаких шагов вперёд без ревью.
- Никакого смешения этапов в одном коммите.
- Никакого слепого принятия замечаний ТБ — LLM врут, проверяй сам (арбитраж — несущая стена).
- Никаких чужих изменений в коммитах такта.
- Основной процесс НЕ оценивает код до сбора всех ответов ТБ (по умолчанию два бога: Codex + АГ; ЧК подключается ТОЛЬКО по явному слову юзера «с чк»/«полный ТБ»/«чк-макс»). Первичный blind-review делают внешние боги; основной процесс — арбитр. Это убирает author-bias.
- Push, amend, rebase, force-push, --no-verify — только по явному разрешению на конкретное действие.

## Алгоритм

### 0. Preflight и инициализация (один раз на задачу)

**Проверка среды:**
- `git rev-parse --is-inside-work-tree` — внутри git-репо? Если нет — стоп, спросить юзера.
- `git status --short --branch` — узнать ветку, upstream, dirty state.
- Если HEAD отсутствует (репо без коммитов) — отметить `initial commit mode`, использовать staged diff для ревью.
- Если working tree dirty (есть staged/unstaged до старта) — перечислить файлы и спросить юзера: что относится к новой задаче, что к старой работе. **Не трогать чужие изменения** — не stash, не reset, не commit без явного разрешения.
- Если ветка `main`/`master`/release/hotfix или detached HEAD — спросить, создать ли feature-ветку.

**Согласование политики:**
- Разрешён ли push? На какой remote/branch?
- Push после каждого такта или только финальный?
- Есть ли pre-commit hooks / CI? Какие команды для тестов/линта?

**Декомпозиция:**
- Разбить задачу на дискретные такты с границами (какие файлы/модули/функции трогаются).
- Озвучить план юзеру: список тактов, ожидаемые коммиты, критерии завершения каждого.
- Дождаться подтверждения / правок плана.

### 1. Реализация такта N
- Зафиксировать baseline: текущий commit hash, branch, status.
- **Тест-гейт (красный → зелёный):** такт меняет поведение, покрываемое тестами → сначала написать/обновить тест на это поведение и убедиться, что он ПАДАЕТ на старом коде (зелёный сразу = тест не ловит дельту), затем реализация, затем тест зелёный. Такты конфиг/доки/рефакторинг без смены поведения — гейт неприменим, отметить причину в журнале.
- **Root cause для bugfix-такта:** перед кодом зафиксировать корневую причину (симптом → воспроизведение/доказательство → где именно ломается → почему старое поведение неверно). Фикс без названной причины запрещён — иначе лечится симптом, а не болезнь.
- Сделать ровно один этап. Никакого "заодно поправил".
- Не лезть в файлы вне границ такта (даже если видно опечатку — отметить как future takt).
- Если по ходу видно, что границы выбраны неудачно — стоп, переговорить с юзером.

### 2. Diff-проверка → commit (push откладываем до после ТБ)

**Перед staging:**
- Запустить релевантные тесты/линтеры если они доступны и не требуют интерактивного ввода.
- Просмотреть `git diff` (unstaged) и `git diff --cached` (staged) — убедиться:
  - в diff только изменения такта;
  - нет чужих user edits;
  - нет секретов: API ключей, токенов, паролей, приватных ключей, `.env` с реальными значениями;
  - нет случайного обнуления production credentials/config.
- При подозрении на секрет или разрушительное изменение — **стоп**, не commit, спросить юзера.

**Commit:**
- `git add <только файлы такта>` — не `git add -A` без необходимости.
- Сообщение: `такт N: <что сделано>` (одна короткая строка).
- Если pre-commit падает — чинить причину, **НЕ** ставить `--no-verify`.
- Не использовать `commit --amend`, rebase/squash, не переписывать уже-проверенные коммиты.

**Push (если разрешён) — ТОЛЬКО после закрытия ТБ-ревью и фиксов (шаги 3-5):**
- Непроверенный код в remote не пушим. Сначала ТБ + арбитраж + фиксы, потом push проверенного.
- Если upstream отсутствует — спросить перед `git push -u`.
- При non-fast-forward / merge conflict — **стоп**, не делать auto-pull/auto-rebase, спросить юзера.

### 3. ТБ-ревью (по skill `tb` — единый источник правды)

ТБ = независимые внешние оценщики (по умолчанию ДВА: Codex + АГ; ЧК — третий, только по явному слову юзера) + основной процесс как арбитр. Полное определение, команды и формат — в skill `tb`.

**Основной процесс НЕ ревьюит первым.** Своё мнение по коммиту до сбора всех ответов богов не формирую — это убирает author-bias (автор свежего кода не способен на blind review). Первичный blind-review делают внешние боги.

**Подготовка артефакта (всем богам одинаковый):**
- Формат — по skill `tb`: один файл `<repo>/.tb-artifact.md` (временный, не коммитить), внутри интент + кумулятивный diff `git diff <base>..HEAD` от зафиксированной базы такта (staged diff в initial-commit-mode); всем богам — путь к файлу.
- Исключить шум: lock-files (`*-lock.*`, `*.lock`, `go.sum`), минифицированный код (`*.min.js`, `dist/*`), сгенерированный код.
- Если diff > ~1500 строк осмысленного кода — chunked review: file-level summary + diff по ключевым файлам, либо спросить юзера разрешения пропустить ТБ для этого такта.
- Единый формат findings (`[severity] file:line — проблема — фикс — уверенность`). **НЕ включать свои рассуждения «почему я так сделал»** — иначе заражаешь blind-review.

**Промпт для оценщиков:**
- Системка = ядро v2 (божественный промпт из `~/.claude/CLAUDE.md`) + ТБ-надстройка (дословный текст — skill `tb`; аудиторская роль, coverage-first и read-only уже внутри).
- Fallback, если CLAUDE.md/skill недоступны: "Ты независимый аудитор кода. Репорть ВСЕ найденные проблемы, включая неуверенные и мелкие: файл:строка + сценарий отказа + severity + уверенность. НЕ фильтруй сам «по важности» — фильтрует арбитр ниже по конвейеру, твоя метрика — покрытие. Не выдумывай: каждая находка опирается на конкретный код; «чисто» — валидный ответ. Файлы не менять, код не запускать — только анализ." (Формулировку «ищи только критический урон» НЕ использовать — современные модели исполняют её буквально и молча роняют recall.)

**Вызов — все боги прогона параллельно (точные параметры — skill `tb`, единый источник правды):**
- **Codex:** `mcp__codex__codex` single-shot (без `model` — сток из `~/.codex/config.toml`; ядро v2 + ТБ-надстройка + задача склеены в `prompt`), `approval-policy: "never"`, `sandbox: "danger-full-access"`.
- **Gemini-плечо = Antigravity (АГ):** `mcp__antigravity__ask-antigravity`, `prompt_file` = абсолютный путь к артефакту, системка (ядро v2 + ТБ-надстройка) — в параметр `system`.
- **[РЕЗЕРВ — только по явному слову юзера «с чк» / «чк-макс»] Чистый Клод (ЧК):** отдельный процесс `claude -p ... --model claude-opus-4-8 --effort high --disallowedTools "Edit Write NotebookEdit"` (полная команда — в skill `tb`).
  Раунды — в артефакт-файл добавлять историю прошлого раунда (принято/отклонено + почему), всем богам одинаково (см. skill `tb`).
- Codex+АГ — в одном tool-use блоке, параллельно; ЧК (если позван юзером) — в том же блоке через Bash(run_in_background). Собрать ответы всех участвующих богов.
- **Лимит ретраев: 2** на оценщика. После 2 ретраев → **ТБ неполный, спросить юзера**: ждать / частичный ТБ / подключить ЧК (только по явному «да» юзера) / выйти. **Не зацикливать.** НЕ заменять упавшего бога самим основным процессом — это вернёт author-bias.

### 4. Арбитраж замечаний (основной процесс — здесь впервые оценивает код)

- Скомпоновать ответы всех богов прогона: дедуп (одно и то же нашли несколько богов → high-priority), сортировка по severity.
- По каждому замечанию проверить по коду: воспроизводится ли проблема? валиден ли фикс?
- Перед фиксом bug-замечания назвать корневую причину (какое предположение/инвариант нарушено), а не только симптом-вход. Фикс закрывает класс проблемы, не единичный вход.
- **Цель — не пропустить баг.** Сомневаешься → считаешь баг реальным (перестраховка).
- Отклонять замечание **только с доказательством из кода/ТЗ**. НИКОГДА не отклонять по «я так задумал» — спорный инвариант вернуть богу на проверку.
- Совпадение нескольких богов повышает приоритет, но **не заменяет** локальную верификацию.
- Несовместимые фиксы → не применять оба. Выбрать один с обоснованием или эскалировать юзеру (вариант каждого бога прогона + игнор).
- Замечание требует выхода за границы такта → пометить как future takt, **если** не блокирующий баг текущего коммита.
- Любое security / data-loss / production-breaking замечание — блокирующее до проверки.
- Сводка таблицей: замечание / валидно? / принято? / обоснование.

### 5. Применение фиксов

- Валидные → минимальный diff в границах такта.
- Отдельный коммит: `такт N fix: <что>`.
- **Повторное ТБ обязательно**, если fix меняет: runtime behavior, security, tests, migrations, API, config, build. Возврат к шагу 3 для fix-коммита.
- **Стоп-патчить:** фикс на ОДНО и то же замечание не прошёл повторное ТБ 2 раза подряд → третью заплатку не клеить. Пересмотреть подход/границы такта (возможно, кривой инвариант или неудачная декомпозиция), при необходимости эскалировать юзеру.
- Чистая косметика / комментарии / форматирование → повторное ревью можно пропустить **только если** юзер заранее разрешил cosmetic exception. Иначе ревью обязательно.
- Невалидные замечания → одной строкой в журнал: что отклонили / чем проверили.
- **Не amend** уже-запушенный или уже-проверенный коммит без явной команды юзера.

### 6. Push (если разрешён) и переход к такту N+1

- Push разрешённого, уже проверенного кода (если push policy = после каждого такта). Непроверенного в remote нет — ТБ уже закрыт.
- Только после полного закрытия шага 5 (включая повторные ТБ-циклы fix-коммитов).
- **Свежее доказательство:** перед финальным отчётом такта — прогон релевантных тестов/линта В ЭТОМ цикле (после всех фиксов). В отчёт — фактический результат (passed/failed, exit code), а не «должно работать». Нет свежего прогона → нельзя объявлять «такт закрыт». Тестов в проекте нет → честно писать «тестов нет», прогнать что есть (сборка/линт).
- Кратко отчитаться юзеру: что сделано, какие коммиты, какие замечания приняты/отклонены.
- Возврат к шагу 1.

## Жёсткие правила

- ЗАПРЕТ на `--no-verify`, `--no-gpg-sign`, `commit --amend`, rebase / squash, force-push без явной команды юзера на конкретное действие.
- ЗАПРЕТ на auto-pull / auto-rebase при non-fast-forward push — сначала спросить.
- ЗАПРЕТ на коммит чужих стартовых изменений без явного разрешения.
- ЗАПРЕТ на коммит секретов, приватных ключей, токенов, `.env` с реальными значениями.
- ЗАПРЕТ на пропуск ТБ — исключение только по прямой команде юзера, с пометкой rule-break в журнале.
- ЗАПРЕТ на смешение этапов в одном коммите.
- ЗАПРЕТ на работу над тактом N+1, пока такт N и обязательные fix-review циклы не закрыты.
- ЗАПРЕТ на «готово / работает / такт закрыт» без свежего доказательства (прогон в текущем цикле с фактическим выводом). «Должно работать» / «выглядит верно» без прогона — нарушение.
- ЗАПРЕТ на оценку кода основным процессом до сбора всех ответов ТБ (анти-author-bias). Основной процесс — арбитр, не co-reviewer.
- ЗАПРЕТ на изменения вне границ такта (даже опечатку в соседнем файле) — это в future takt.
- Задача проще плана → можно объединить такты только после согласования.
- Задача сложнее → можно дробить такт только после согласования.

## Команды режима

- `следующий такт` — перейти к N+1 (только если шаг 5 закрыт; иначе отказать с указанием блокера).
- `повтори ревью` — отправить тот же коммит в ТБ ещё раз.
- `пропусти ТБ на этом такте` — переспросить подтверждение, выполнить только при явном "да", отметить rule-break.
- `статус ТАКТ` — показать: текущий такт, branch / upstream, последний коммит, состояние ТБ-ревью, блокеры.
- `останови ТАКТ` — остановить workflow без удаления изменений и без git reset.
- `выйти из ТАКТ` — закрыть режим, дальше работать обычно.
- `покажи план` — список тактов со статусом.

## Журнал такта

Для каждого такта проговаривать в чат:
- Номер такта и границы (файлы / модули).
- Branch / upstream / стартовый git status.
- Что сделано (1-2 строки).
- Проверки перед коммитом: tests / lint / secret scan — что прошло.
- Тест-гейт: какой тест падал до реализации и позеленел после (или почему гейт неприменим).
- Финальный прогон после фиксов: фактический результат (passed/failed).
- Хеш коммита (короткий).
- Push status: не пушилось / pushed / blocked.
- Сводка ТБ: total замечаний / валидных / принятых.
- Применённые фиксы (хеши).
- Отклонённые замечания с причиной.

## Edge cases

- "Сделай маленький фикс" без явного ТАКТ → не активировать.
- Не git-репозиторий → стоп, спросить юзера: переключаться или работать без ТАКТ.
- Dirty working tree на старте → не трогать чужое, спросить про принадлежность файлов.
- Уже есть staged changes до начала → не commit автоматически, спросить.
- Первый коммит в репозитории (нет HEAD) → initial-commit mode, использовать staged diff.
- Ветка main / master / protected / detached HEAD → спросить про feature-ветку и push policy.
- Нет remote / upstream → commit можно, push — только после отдельного разрешения.
- Pre-commit падает → чинить причину, не обходить.
- Интерактивный prompt в Bash (пароль, SSH ключ, `git push` запрашивает auth) → стоп, эскалация юзеру.
- Один из ТБ молчит / упал / модель не найдена → 2 ретрая максимум, потом эскалация.
- Diff не помещается в контекст → chunked summary + key files, не пропускать changed-files список.
- ТБ предложили несовместимые фиксы → проверить оба, выбрать один с аргументом или спросить.
- ТБ предлагает рефакторинг вне границ такта → future takt.
- Юзер посреди такта: "переделай иначе" → остановить, обновить план, не смешивать scope.
- Коммит уже запушен, ТБ нашёл серьёзный баг → fix-коммит сверху, не amend, не force-push.
- Большие auto-генерируемые файлы (lock, dist, generated) → исключать из ревью diff'а, но коммитить как есть.
